# D02: action consequences and resource transitions

Prepared October 3, 2026. **Proposed; awaiting Vanna's decision. No implementation or approval.** Owning baseline: `eb7ac8c4ff95842f21b1427828182dd79483bf6e`. Extends [ADR-0006](../adr/ADR-0006-declared-actions-and-owner-attributes.md) for G03/G04 in the [remediation plan](../continuity-gap-remediation-plan.md). Read alongside the frozen [payloads](d02/payloads.json), [acceptance fixtures](d02/acceptance.md), and [compatibility/authority review](d02/review.md).

## Decision requested

Approve one optional, closed `consequenceContract` on `ActionDefinition`. For new/adopted/revised actions and events it is mandatory; an explicit empty contract means no effects are permitted. Each bounded slot declares its target owner role, property, required/optional presence, condition, exact assignment or signed resource delta, order and lifetime. Events still supply existing `EntityEffect` propositions and generate existing assertions. Validate the complete effect list against the definition; never insert a missing cost, repair a wrong recipient, or recompute an author's proposed post-value silently. No new public tool, event field, resource ledger, simulation scheduler or model role.

This is the smallest useful extension: required slots prevent omitted consumption; a closed allowlist prevents unrelated grants; role binding prevents recipient substitution; a checked delta prevents invented balances. Requirements remain separate preconditions. An empty requirements list does **not** imply unconstrained consequences.

Material choices needing Vanna's decision: (1) explicit contracts required for touched legacy records, with immutable untouched history readable but uncertified; (2) integer counts and integer quantities in one exact unit only; (3) unresolved conditions block occurred events even for optional slots; (4) distinct exact authored times for dependent separate events; (5) definition revisions revalidate all bound events in the candidate. The recommendation includes all five. Acceptance of this document authorizes a later implementation task, not canon changes or an automatic migration.

## Closed payload contract

Use canonical domain camelCase; tagged variants use snake_case. Proposed types reject duplicate/unknown fields. Wire namespace expansion remains existing behavior; canonical references always name the universe. All references resolve in the exact candidate revision, never mutable global head. Full synthetic payloads use valid ID shapes but name no live resources.

`consequenceContract: ConsequenceContractV1?` is omitted on serialization when absent (never defaulted to empty); body is `{kind:"action_consequences_v1", slots:[EffectSlot]}`. Unknown kind is unsupported, not unrestricted. Explicit null is invalid wire input. The proposed Option implementation must distinguish/reject null during input decoding rather than relying on ordinary Option deserialization.

`EffectSlot = {slot, order, presence, target, condition, change, lifetime}`; all fields required. `presence` is `required` or `optional`. `target={role, predicate:RecordRef}` identifies the proposition subject via exactly one entity participant in that event role. V1 is property-only: proposition `roles` must be absent/empty, `quantification=particular`, `context=action.scope.context`, and value must conform to that property. No free recipient, relational roles, predicate wildcard, label matching, variable value expression, or unrelated extra proposition binding. Existing action prerequisites can still name other owners. Duplicate role participants, nonentities and cross-universe references fail. Every mentioned role, including a condition-only role, resolves uniquely even when its condition is false.

`condition` is `{kind:"always"}` or `{kind:"attribute_equals", role, predicate:RecordRef, value:Value}`. The latter reuses owner-bound exact pre-event attribute evidence from ADR-0006; it is not a caller Boolean or a general expression language. `change` is either `{kind:"set", polarity:"support"|"refutation", value:Value}` or `{kind:"delta", delta:string, minimum:string, maximum:string, unit:UnitId|null}`. Delta is support-only, property multiplicity must be single, and its property shape must be Integer or Quantity with an Integer magnitude and the exact declared unit. A set permits an authored fixed value only; setting a resource to an arbitrary caller amount is impossible. Explicit replenishment may use a positive delta or an author-approved fixed reset action; no global conservation is inferred from property names. An unlimited-ammunition genre action explicitly declares no stock slot; that classification needs author/prose review.

`lifetime` is `{kind:"until_changed"}` or `{kind:"ticks", count:string}`. Both produce existing explicit calendar intervals starting exactly at the event. Until_changed requires unbounded authored end; existing event expansion may shorten it at a later superseding generated effect. Ticks requires a positive count and checked exact `end=time+count`. This prevents a caller turning a brief grant into permanent power. Expiry does not synthesize a resource refund. V1 deltas require until_changed; expiry of a balance cannot restore an older value. Sets may use either. Existing non-event evidence is never silently ended; authors must explicitly end/supersede incompatible evidence in the same proposal.

Bounds: at most 64 slots per action (fits the current 100-effects event cap); unique nonempty slot names and roles of at most 120 UTF-8 bytes; unique explicit order values in 0..63; condition/value follow existing bounded domain types. No two slots may resolve to the same `(subject, predicate, context, scope)` state key in one event, including aliases where two role names name one entity. Reject overlapping target worlds as well. Thus order fixes presentation/expansion, not an intra-event calculator. Transfers use distinct debit/credit owners with equal and opposite declared deltas; reject same-owner aliasing, and require both slots in the same atomic event. V1 deliberately omits loops, variable costs, rational conversions and dependent phases. Later need requires another decision.

## Exact scope and evidence semantics

For a transfer the paired fixed debit/credit amounts are visible in the contract and independently sum to zero in its acceptance fixture; no transfer behavior is inferred from the action key or label. Other definitions may explicitly create or destroy stock through authorized deltas.

Definition scope retains existing universe-wide or explicit nonempty world-set applicability, represented context, no realm, and validity (unspecified vocabulary validity remains revision-wide). Event must fall within definition scope. For effects, strengthen existing first-effect checks: **every** slot's proposition and assertion must use the definition's context; applicability must equal the event's full effective scope. Empty event worlds means universe-wide; a world-scoped action cannot use empty worlds. Nonempty event worlds means exactly that canonical world set, which must be a subset of action worlds if bounded. No duplicate worlds, realm, extra scope qualifiers, partial-world consumption, or mixing objective and belief effects. The concrete examples use a single world. Universe-wide contract execution additionally resolves pre-evidence at the universe-wide scope; never borrow a convenient single-world balance. Multiworld execution calculates in every affected world: one shared post-proposition is legal only if all worlds independently yield the same required post-value. Otherwise author separate scoped events.

All action requirements and conditions read immediately before the event at its exact named-calendar coordinate; event effects cannot bootstrap them. A condition is true only with complete, exact, unopposed support for the requested value. It is false only with complete established contrary evidence (explicit active refutation or a unique supported incompatible single-valued attribute), not absence. Missing, conflicting, expired, alternative-valued, unknown-time, restricted or incomplete evidence is unresolved. For occurred events unresolved conditions deny admission, retaining unresolved diagnostic status. If true: required slot exactly once, optional slot zero or once. If false: slot absent. Always uses true. No unlisted slot, duplicate, mismatched order, value, polarity, target or lifetime is admitted. Conditional required means required when true, not unconditionally required. A disabled or omitted optional delta does not consume or require stock evidence; its condition still needs a resolved truth value. Resource hazards include only enabled present/required slots, while action requirements and condition reads always contribute their actual dependency keys.

Non-occurred events validate declared slot membership, target bindings, shapes and scope, but do not execute accounting, require present required slots, resolve condition truth or establish objective assertions. Changing occurrence to occurred performs the full contract check; planned effects cannot grant a precondition.

For each enabled delta slot that is present (or required and missing), discover all applicable direct/generated assertion evidence for the precise owner/property/scope at the pre-event boundary. A proposition alone, item-power-derived value, refutation alone, rough range or absent balance cannot establish stock. Require one unique exact supported magnitude, no active conflicting/refuting/uncertain alternatives, matching unit and explicitly applicable validity. Multiple agreeing evidence chains can corroborate one value; record all dependencies. No closed-world zero and no implicit unit conversion. An exact historical event-generated balance may provide current pre-evidence even if its original action lacks a consequence contract; this certifies the new transition only, not the historical action's cost or legitimacy. A nonempty world set may use applicable universe-wide evidence only if all affected-world evaluations agree and contain no contrary evidence. Restricted evidence must not be disclosed in diagnostics; inability to finish the existing visibility/validation route never becomes an authorization.

Pre-value is derived evidence, not a new mutable field on Event. The submitted effect proposition contains the exact post-value. Validation's consequence detail records exact action version, slot, owner/property/scope, pre evidence versions/magnitude, signed delta, calculated post, submitted post and disposition. These details are proposed diagnostic data bound through the existing execution digest; no second source of canon authority. Missing evidence records no invented pre/post. For set effects, validation records the fixed required post and condition evidence; there is no mandatory prior value unless declared as an existing action requirement.

## Bounded accounting and ordering

All integer inputs use canonical decimal strings (`0` or signed nonzero digits, no leading zeros, `+`, whitespace or `-0`); at most 39 digits and within signed i128. Delta cannot be zero; `minimum <= maximum`; pre and post both within authored bounds. Checked addition rejects overflow before comparing post. Unit null means dimensionless Integer; otherwise exact integer Quantity in that unit. No floats, rounding, inferred conversions, debt beyond the authored minimum, or unlimited sentinel. Time arithmetic uses the same signed bound checks and excludes i128 endpoints as current event coordinates do. A single event validates all slots against one common pre-state and publishes all effects atomically; failure admits none.

Two events at the same coordinate do not acquire order from IDs, list order, `sequence`, effect order, proposal submission order or receipt order. Preserve events-v1 rejection of same-time noncommuting writes. Add consequence dependency checks: same-time read/write or write/write overlap of a constrained balance or condition/requirement key denies both, even if both post-values agree. Across universe-wide/world scopes overlap counts; disjoint contexts/worlds/owners may commute. Uncomparable calendars/time remain unresolved for interacting keys. Author distinct exact coordinates, e.g. 10 then 11; at 11 the generated balance from 10 supplies pre-evidence. An atomic debit/credit transfer uses one event; multiple uses of the same stock cannot be packed into separate same-time events. Exact pre-event semantics remain `[start < t <= end]`; post queries are `[start <= t < end]`.

## Compatibility, authority and invalidation

Historical action definitions with absent consequenceContract serialize to the same canonical bytes and retain digests; untouched actionless/contractless historical events remain readable and are explicitly excluded from consequence-certified coverage. They still undergo existing structural/event checks. Do not retrospectively label their effects legal under D02. Any new/adopted/revised event must name a contract-bearing action, even for empty effects; any new/adopted/revised action definition must supply a contract. Unrelated edits may retain untouched legacy records with a visible scoped coverage exclusion, preserving existing raw-record admission. An implementation must expose that exclusion separately from successful checks, not fabricate universal consequence certification.

Adding a contract to an existing action is a protected definition revision with expected version, same namespace/key and exact author approval. It revalidates **every** event currently bound to that action, including unchanged historical events, against the new contract; missing effects require explicit event correction/tombstone or a different explicitly authored action. Migration is opt-in and proposal-scoped, never startup rewriting. If past intended behavior genuinely differs, keep immutable old editions and define a new action identity for future use. Existing events referencing contract-bearing actions are always rechecked even when unchanged. Removing a contract from a previously contracted definition is forbidden in a new candidate; an explicit empty contract is a visible protected retcon, not an escape. Adoption must not smuggle a contractless event or downgrade a contracted action.

Current code already classifies actions as protected definitions, forbids delegated protected commits, expands effects before freezing proposals, verifies generated assertions exactly, and binds evaluator/approval/proposal/base head/assessment selection and current authority. Preserve those gates. No model, evaluator result, successful proof script, source assessment or action definition grants write permission. Scope/entity/predicate boundaries cover complete generated assertion changes, debit and credit recipients, and automatic interval endings in other events. Protected definition changes require current definition permission **and** exact installation-author approval; bounded ordinary-event delegation remains available only under existing complete-validation and current-grant conditions.

A definition, property/unit/context/world, participant binding, condition evidence, starting balance, earlier event, interval or time retcon changes the candidate snapshot. Reexpand generated intervals, calculate all bound events anew, and expose dependent failures. Do not silently fix later post-values. Revise/resubmit yields a new proposal digest; prior validation/approval/assessment bindings cannot publish it. Head drift, evaluator upgrade, authority revocation/expiry, selection changes or changed execution details invalidate the old final binding under existing publication checks. Bump EVALUATOR for D02 semantics; keep `events-v1` identity recipe because assertion expansion itself is unchanged. If expansion semantics must change, stop and propose an explicit version/migration decision. Old revisions and exact historical evidence remain reproducible and are never updated by the new candidate.

## Implementation slices after decision

1. Domain/schema: optional omitted contract and closed bounded slot DTOs; canonical historical byte/digest fixtures, strict null/version handling, namespace normalization, dependency traversal, shape/lifetime/scope/role validation. Regenerate checked schema/tool catalog using existing process. No additional MCP tools.
2. Service/rules: slot matching and condition/pre-balance resolution after candidate reexpansion; checked arithmetic and interacting-key conflict detection; touched-record compatibility and all-bound-event revalidation. Preserve generated IDs and existing assertion guard. Freeze diagnostic result in existing execution binding.
3. Workflow/authority: evaluator bump; author review shows definition diff, pre/post evidence, generated interval changes, exclusions and retcon impact; enforce old/new footprint and full entity/predicate boundaries on generated changes; exercise stale approvals, assessments, authority and restart.
4. Existing typed action/event UI and clients: expose contract slots and the existing proposed post-value, reject unsupported variants visibly, show condition/unresolved/mismatch information; do not silently fill omitted action/contract/cost. Native interaction remains a separate qualification gate.
5. Qualify frozen fixtures with actual proposal → validation → denied/approved commit attempts, package history/restart and independent accounting audit; full existing workspace/schema gates. P1/P2 structural proofs precede P3 prose extraction of implicit consumption/wrong ownership. No unrestricted simulation or prose completeness claim.

## Alternatives and limits

Free-form prose consequences cannot enforce costs or targets. Inferring effects from labels adds unauthored physics. A standalone balance ledger duplicates canon and expands atomicity/retcon work. Automatic post-value generation would hide omitted/forged effects from author review; use explicit propositions and verify them. Full expressions, decimal/rational conversion, variable amounts and same-time scheduling offer more flexibility but exceed the demonstrated minimum. Integer quantities can represent cents or authored mana ticks; new unit schemes require protected author decisions. V1 supports bounded authored consumption, transfers, replenishment and fixed grants; it does not certify conservation across every possible author-approved reset action, ensure extraction of all prose consequences, or prevent an author deliberately declaring an unlimited action.
