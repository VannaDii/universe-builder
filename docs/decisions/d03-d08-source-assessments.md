# D03/D08: source assessments and validation scope

Prepared October 2, 2026. **Recommendation approved by Vanna on October 2, 2026; implementation remains separate.** This document specifies workflow contracts; the proof artifacts establish decision-preparation evidence rather than canon authority. See the approval record below. Scope follows [D03/D08 in the remediation plan](../continuity-gap-remediation-plan.md).

## Concrete decision

Recommend one typed, immutable `SourceAssessmentV1` attached to an **already submitted, frozen proposal version**, with an independently versioned selection record. Keep it outside canonical domain operations and outside the existing proposal digest. Final validation binds the candidate, selected assessment identity/digest (or explicit absence), selection generation, exact submitted scope and evaluator. Existing exact author approval/delegation and commit remain authoritative. A positive assessment is the assessor's declared conclusion about its declared inventory and sources, never engine-verified natural-language entailment or arbitrary manuscript completeness.

Vanna approved the recommendation above. The supporting payload, lifecycle, compatibility and host-selection details are specified below. The material tradeoff is explicit: immutable evidence and exact approval binding require extra storage, full source/dependency visibility, revalidation after replacement and coordinated client upgrades. Ordinary raw source/evidence archiving remains available. D03/D08 do not invent new semantic predicates, universal blockers or model roles.

## Typed assessment body

All types are closed, versioned, snake_case workflow DTOs, with duplicate and unknown fields rejected. Domain references/value/time/scope types retain their existing wire shapes; do not copy workflow naming into canonical records. Full examples and exact bytes are in [d03-d08/examples.json](d03-d08/examples.json). IDs in those examples are synthetic, valid-prefix-shaped values, not live resources.

`AssessmentEnvelope { assessment_id: AssessmentId, digest: Sha256Hex, body: SourceAssessmentV1 }`. ID and digest are assigned by the service after verifying the authenticated body. `AssessmentId` is a workflow identity, not RecordId. Neither appears inside its own hashed body. `Sha256Hex` is exactly 64 lower-case hex characters. The service computes every digest and compares supplied content hashes with actual stored bytes; caller hashes are not authority.

| Body member | Required type and rule |
|---|---|
| `kind` | Literal `source_assessment_v1`; schema discriminator included in canonical body hash. |
| `proposal` | Existing ProposalRef: exact ID/version/digest of latest submitted, nonwithdrawn frozen proposal. Submit/revise changes the proposal digest and requires a new attachment. |
| `base_frame` | Existing Frame, byte-equivalent canonical value to the proposal frame. Universe, continuity, revision, represented context, perspective, time, optional readerScene and personalSequence all bind. Assessment VersionRef fields require explicit universe even though the reusable domain type permits its omission; reject cross-universe references and conflicting versions of the same active record. |
| `assessor` | `{principal: PrincipalId, method: Method, tool: ToolIdentity|null, assessed_at: RFC3339Utc}`. Service derives principal from authenticated ProfileId using existing conversion; Method = `human_review` or `external_model_review`. ToolIdentity = `{name, version, model_revision, procedure_digest}` with nonempty strings and SHA256 procedure digest. Model/tool labels are externally asserted provenance, not authenticated identities or trust grants. Human review uses null tool; external_model_review requires ToolIdentity. Editorial timestamp is not story time. |
| `sources` | Nonempty ordered list of SourceBinding: `{key, source_version: VersionRef, blob_digest, byte_size, representation:"exact-utf8-v1", ranges:[ByteRange], work_edition:VersionRef|null, passage_id:string|null}`. SourceVersion and WorkVersion record payloads must resolve exactly; no `head`, URL fetch, mutable label or implicit newest edition. Every range is half-open, nonempty, UTF-8 aligned and within bytes. Source metadata/staging verified via existing author route. A null edition denotes a passage not tied to an edition, never a manuscript assessment. |
| `dependencies` | Ordered unique exact VersionRef list for all referenced unchanged facts, definitions, rules, contexts, entities, worlds, scene/knowledge/action records and versioned work binding. Every dependency resolves in the frozen candidate or explicitly named immutable historical edition. Ordinary current-state facts must be active candidate versions. Historical provenance never substitutes for current prerequisites. Candidate digest/base revision also bind the entire snapshot, not only this volunteered list. |
| `declared_inventory` | Ordered list of MaterialItem `{item_id, source_key, range:ByteRange, material_kind, statement, mapping_ids:[string], unresolved_ids:[string]}`. MaterialKind = `fact`, `action`, `prerequisite`, `effect`, `knowledge`, `description`, `disclosure`, `unchanged_state`. Statement is review prose, not executable expression. IDs unique; every item range is UTF-8 aligned and contained in a declared range of its named source. Mapping/item and unresolved/item links must agree bidirectionally; dangling IDs or linked items from another source scope reject. Each item links at least one mapping or unresolved item. No material item can silently fall out of the result. Empty inventory is permitted only with `inventory_declaration.kind=no_material_claims` and a nonempty rationale; that declaration in turn requires empty inventory, mappings and unresolved lists. A nonempty inventory requires material_inventory_declared. This remains an assessor declaration, not proof. |
| `inventory_declaration` | `{kind:"material_inventory_declared"|"no_material_claims", rationale:string, exclusions:[{source_key,range,reason}]}`. Explicit exclusions lie inside submitted ranges. Each source/range remains visible as submitted even if excluded. Byte coverage is not semantic material recall. |
| `claim_mappings` | Ordered list of ClaimMapping defined below. Unique mapping IDs, every mapping linked from inventory. No automatic record creation or operation compilation from prose. |
| `unresolved` | Ordered list `{unresolved_id,item_ids,reason,detail}`. Reason = `ambiguous_referent`, `ambiguous_modality`, `unsupported_semantics`, `missing_evidence`, `unrepresented_material`, `interpretation_disagreement`. Must link inventory items; scope-wide concerns use all affected IDs or a separate submitted-range inventory item. Restricted dependencies do not become publicly describable unresolved entries. |
| `conclusion` | `consistent_with_declared_inventory`, `inconsistent`, or `unresolved`. Consistent requires no unresolved entries, no unresolved/contradicted mappings, and every material item covered. Inconsistent requires at least one contradicted mapping; it can coexist with unresolved items. Otherwise unresolved. This validates internal accounting, not whether the assessor extracted all material claims or chose the right meaning. |

`ClaimMapping { mapping_id, item_ids, referents:[VersionRef], context:VersionRef, world:VersionRef|null, realm:VersionRef|null, story_time:TemporalExpression, narration_position:Position, reader_position:Position, occurrence:Occurrence, modality:Modality, semantic:SemanticMapping, candidate_links:[CandidateLink], judgment:MappingJudgment, rationale:string }`.

- Position is closed `{kind:"not_applicable"}`, `{kind:"unknown",reason}`, or `{kind:"work_position",work_edition:VersionRef,scene_id,ordinal:u64}`. Unknown does not imply consistent. Exact story time uses existing domain TemporalExpression; ambiguous/unknown time remains explicitly unresolved when material.
- Occurrence = `occurred`, `planned`, `hypothetical`, `reported`, `unknown`. Modality = `asserted`, `negated`, `possible`, `counterfactual`, `attributed`, `unknown`. Context/occurrence/modality/negation are bound independently; reported speech cannot silently become objective truth.
- SemanticMapping is tagged `claim {predicate:VersionRef,subject:VersionRef,value:Value,roles:[{role,participant:VersionRef}],polarity:Polarity}`, `action {action:VersionRef,participants:[{role,participant:VersionRef}],prerequisites:[VersionRef],effects:[VersionRef]}`, `knowledge {holder:VersionRef,content:VersionRef,acquisition:[VersionRef]}`, or `source_description {subject:VersionRef,depiction:"factual"|"subjective"|"inspiration",implied_claims:[VersionRef]}`. Unsupported semantics stay unresolved; these DTOs do not implement D02–D07/D09 or pixel interpretation. Empty lists are explicit, not missing fields.
- CandidateLink = `{kind:"proposed_record"|"unchanged_record"|"historical_evidence",version:VersionRef}`. Proposed links must resolve to exact compiled next versions. Unchanged links must resolve to active candidate records not replaced by the proposal; historical evidence must be an exact accessible version and labeled as such. Every reference also appears in `dependencies` or `sources` (including work edition). Lists retain authored order; duplicate entries rejected instead of silently normalizing ambiguous mappings.
- Material unknown story time, narration/reader position, occurrence, modality or referent requires an unresolved mapping plus a reciprocally linked unresolved item, preventing a consistent conclusion. Irrelevant narration/reader positions use not_applicable; unknown is never a substitute for not_applicable. A contradicted known mapping can coexist with other unresolved material and retain inconsistent conclusion. Every unresolved mapping has a linked unresolved disposition; every unresolved disposition names declared material.
- MappingJudgment = `supported`, `contradicted`, `unresolved`. Bytes are verified independently by the service; a supported judgment is the assessor's semantic claim. A known error in an attached interpretation requires replacement, not editing history.

Limits follow the current 1 MiB frame limit: reject oversize attachments, never truncate inventory to fit. Proposed caps: 64 sources, 4096 inventory items, 4096 mappings, 4096 unresolved entries, 16384 dependencies, 16384 UTF-8 bytes per free-text member. A bounded host may split distinct passages into separate frozen proposals; it may not label a partial attachment as covering omitted text. Large attachment upload/storage extensions are outside this decision. Paginate authorized review retrieval under pinned assessment digest and selection generation; final approval requires a complete review response/verified pages.

## Acyclic exact binding

Keep the existing candidate digest `C = workflow::hash((proposal_with_empty_digest, compiled_assignments, footprint))`. Do not recompute it from a paged public Proposal or a JSON summary: workflow includes private compiled assignments/footprint and generated versions. The proof fixture includes both the exact production-shaped `(Proposal with empty digest, assignments, footprint)` tuple for a candidate adding a source anchor and an explicitly identified miniature frozen-candidate object for source/mapping arithmetic. The latter is **not** today's production proposal preimage; neither fixture claims runtime admission. The production_bound_example chains the actual-shaped tuple C through body A, selection, correctly serialized execution and final V with the same C throughout. Exact synthetic base/dependency IDs are supplied; their retained snapshot existence is an explicit fixture premise, not observed runtime evidence.

Let `J` be the owning canonical serializer: sorted object keys, no whitespace, preserved UTF-8 strings, ordered arrays, exact integers, no host floats. Body hash `A = SHA256("source-assessment:v1:" || J(body))`. The body contains C but not A, assessment_id or selection generation. Selection is separate `{proposal, generation:u64, selected:AssessmentRef|null}`, where AssessmentRef = `{assessment_id,digest}`. Final binding hash `V = SHA256("source-validation:v1:" || J(binding))`, where binding has `{kind:"source_validation_binding_v1",proposal,base_frame,selection,submitted_input,assessment_state,execution_result_digest,evaluator_version}`. Assessment_state is the exact authorized AssessmentState in the response, excluding restricted; it binds whether the selected attachment is usable, unresolved, stale or unavailable, not merely its ID. Execution_result_digest hashes the complete unpaged existing validation core excluding the new assessment wrapper, **after owning typed serialization**: operation_id=None and empty opposing_evidence are omitted by the current Validation serializer, not hashed as null/empty fields. New assessment DTO nullable fields are explicitly retained as null; their closed output serializer does not skip them. Null and absence are different canonical objects. Run identity stays in that core; approvals remain exact to a particular run. No V or approval is embedded in C, A or the execution core. Existing Checked hash adds the final binding/result; approval still binds full Checked evidence.

Dependency DAG: frozen semantic candidate → immutable assessment → selection and execution evidence → final validation → exact authority → commit receipt. Incorporating A into a canonical operation whose body contains C would require `C=H(...A(C)...)`. Omitting only a `digest` field from that operation would still leave the cycle. Do not iterate toward a hash fixed point or weaken C. Reject self-reference fields and assessment-as-domain-operation outright.

## Attachment lifecycle and invalidation

Preserve the **thirteen public MCP tool names**. In protocol 3 extend universe_propose with closed action variants `attach_assessment {universe,universe_id,context_id,proposal_reference,expected_selection_generation,body,idempotency_key}` and `select_assessment {universe,universe_id,context_id,proposal_reference,expected_selection_generation,assessment_reference:null|AssessmentRef,idempotency_key}`. Dispatch these separately from current semantic create/revise/submit/withdraw so they never increment Proposal.version, alter operations or change C. Extend universe_get_proposal with `view_group:"assessment"` and an optional exact assessment_reference; that view returns the pinned selection generation/current state, and an exact authorized envelope when requested. Its existing proposal_id/version/universe/cursor fields remain; assessment_reference is forbidden outside the assessment view. Retrieval paging binds proposal version, selection generation, exact assessment digest and current authority. Native internal AttachAssessment/SelectAssessment/GetAssessment routes use the same service types; they are not new public tools. These variants are prospective and unavailable in protocol 2. Concrete wire examples are in examples.json.

1. Initial selection generation is 0/selected=null. Attach inserts an immutable body/envelope and atomically selects it at generation+1. Selecting an existing body changes generation; null withdraws selection. Replacement inserts a new identity even with the same semantic verdict. Identical idempotent retries return the original result; mismatched retry rejects. Reselecting the already selected identity is an idempotent no-op only for that exact recovered request, otherwise reject no-change request rather than create unexplained generations.
2. Writes use current propose permission and existing proposal owner/author access. Only the owning authenticated assessor may submit their assessment; author may create her own review. Proposal owner or author may change selection, but cannot impersonate an assessor or alter an existing body. No separate reviewer-role architecture is introduced. Source staging retains existing author-only path; a granted agent may assess already accessible staged/candidate sources, not stage new ones through this endpoint.
3. Stored attachment body is insertion-only, with ID/digest collision checks. Selection history is append-only. Current workflow_put already rejects a changed value under an existing key and permits identical retries. Reuse that immutability for bodies and generation-keyed selection history; atomic compare-and-swap of the latest generation remains an explicit implementation obligation. No historical deletion on replacement/withdrawal. Store all referenced source bytes/versions with existing retention guarantees; if unavailable, status unavailable, never reconstructed from latest text.
4. A stale/cancelled run caused by a concurrent selection/head change returns no final binding and cannot authorize anything. Separately, a **fresh** validation may discover a selected attachment is semantically stale or unavailable while the ordinary structured candidate remains admissible. It then evaluates record-only submitted scope and binds the current selection/generation plus exact stale/unavailable assessment_state in a new V. Existing authority may authorize those records; the private recheck must agree on both state and selection. Source integrity failure still fails existing source verification and cannot be rescued as a record-only success. This preserves raw archiving without reusing an earlier final binding.

5. Validation captures selection generation and identity, checks source bytes/anchors/dependencies, completes accounting and executes existing engine validation. Before persisting success compare generation/head/proposal/current authority. Changes during execution mark result stale/cancelled; retries recover immutable attachment and require a fresh final run.
6. Every selection change, including absence→attachment and attachment→absence, invalidates prior final validation and applicable author approval. Checked/approval compare C, V, A/absence and generation under the same serialization/authority gate used for commit. Commit privately rechecks exact binding and engine admission, atomically compare selection immediately before canonical head publication. No attachment may change in the check-to-commit interval. No receipt/head movement on failure.
7. Any proposal revise/submit/withdraw, changed head/base frame, source/version/anchor/edition selection, mapping/inventory/exclusion, definition/policy version or evaluator contract change makes reuse stale. A changed earlier canon dependency invalidates current continuation even with identical prose. Newer source existing elsewhere alone does not invalidate an assessment of explicitly old edition A; using B instead of A does. Archived A remains meaningful against its exact historical snapshot. A new proposal requires a new body even if all prose bytes match.
8. Assessment history is read-only after canonical commit. A later correction uses a new candidate/assessment; never retroactively relabel an old receipt. Revocation affects current access/commit, not historical integrity. Resume/restart recovers exact immutable IDs and idempotent receipts, not presumed applicability.

## Three independent result axes

New closed, tagged response `ValidationV3 = EvaluatedValidationV3 | RestrictedValidationV3`. EvaluatedValidationV3 is `{kind:"evaluated",execution:Validation,submitted_input:SubmittedInput,assessment:AssessmentState,final_binding_digest:Sha256Hex|null}`. RestrictedValidationV3 is exactly `{kind:"restricted",execution_coverage:"restricted",submitted_input:{kind:"restricted"},assessment:{kind:"restricted"}}`; it carries no proposal/source/assessment IDs, candidate/execution/final digests, counts, excerpts or stale reasons. This explicit restricted shape avoids requiring a hidden-data fingerprint merely to satisfy the normal Validation DTO. A query result or failed/cancelled run has null final_binding_digest and cannot authorize a proposal commit; a completed proposal run can bind a negative/inadmissible result, but existing Checked.admissible still blocks approval/commit. Keep current Coverage values/meaning in `execution.coverage`; no overloaded “complete prose” variant. Delivery.complete/cursor stays a fourth independent delivery property.

SubmittedInput = tagged `query {frame,check_scope}`, `record_candidate {proposal,includes_sources:bool}`, or `source_assessed_candidate {proposal,sources:[SourceBinding],inventory_digest:Sha256Hex}`; `{kind:"restricted"}` is permitted only inside RestrictedValidationV3. Service derives it from actual request/candidate and selected validated attachment, never trusts a caller's “whole book” flag. Source-only proposed records with no attachment are `record_candidate/includes_sources=true`. Complete candidate evaluation scans the whole snapshot, whereas submitted_input declares the text inventory explicitly assessed. An invalid/stale attachment retains record_candidate scope and cannot promote it; a fresh record-only run may have a new final binding including its unusable assessment_state, while discarded prior runs have null binding; authorized details can show claimed stale scope separately. Query-mode results have no proposal authority or source assessment.

AssessmentState is tagged `absent`, `unavailable_legacy`, `restricted`, `unavailable {reason}`, `stale {assessment_reference, reasons:[StaleReason]}`, or `bound {assessment_reference,selection_generation,byte_verification:"verified",declared_conclusion,inventory_count,mapping_count,unresolved_count,inventory_digest}`. Counts and references are never returned in restricted variants. Invalid submitted body fails attachment request rather than producing a bound state. StaleReason = `candidate_changed`, `source_changed`, `edition_changed`, `dependency_changed`, `selection_changed`, `evaluator_changed`. UnavailableReason = `missing_retained_material`, `unsupported_representation`, `failed_or_cancelled_check`. Absence may include no hidden metadata; don't disclose historical attachment existence to unauthorized viewers.

| Execution | Input | Assessment | Meaning and authority |
|---|---|---|---|
| complete | record candidate with source | absent | Bounded checks finished. Source archive is legitimate; no interpreted prose claim. Existing authority can commit. |
| complete | assessed passage A | bound/consistent | Engine finished and assessor declares inventory consistent for A. No claim beyond A or of exhaustive prose understanding. Existing exact approval/delegation still needed. |
| complete | assessed passage A | bound/unresolved or inconsistent | Engine and assessor disagree or material items outstanding. Ordinary record admission remains governed by existing checks; host must not select this prose as assessed consistent. |
| partial | assessed passage A | bound/consistent | Assessor claim survives; engine execution remains partial. Delegation fails Complete gate. Author path possible only if existing admissibility checks pass. |
| any | record candidate | stale/unavailable | No current assessed-continuation claim. New exact validation required for any changed binding. A fresh record-only run can bind current unusable state; a discarded stale run cannot. |
| restricted | undisclosed | restricted | Generic constrained result, no scope/material status leaks and no usable approval evidence. |
| failed/unsupported | any authorized scope | absent/unavailable/bound claim as retained history | No usable completed final run; a historical claim cannot rescue failed admission. |

**Host requirement for assessed continuation:** select persisted passage/edition as assessed consistent only with bound/consistent assessment, no unresolved items, fresh final binding and actual successful canonical commit under existing authority; retrieve persisted text and exact state afresh before continuation. Complete engine coverage is required to advertise completely executed checks; partial author-approved work must say partial. This is a host workflow requirement for the claimed assessed path, not a new universal rule denying raw archive or record commits. A gold extraction failure can invalidate host qualification even when runtime accounting and authority checks pass.

## Visibility and compatibility decision

Assessment read/write scope is the intersection of proposal ownership access and **all** source/edition/referent/dependency/world visibility, including transitive dependencies. Caller access to the changed-record footprint alone is insufficient. Evaluate actual full candidate privately for admission, but do not disclose private result. For partial access return generic restricted/not-accessible, suppress IDs/digests/counts/verdicts/offsets/fingerprints and cursor metadata, not just excerpt text. Native author view obeys authenticated author scope; it is not a new bypass. Paginated attachment access rechecks current authority and pins digest/generation; no existence oracle through lookup or idempotency keys. Review includes declared exclusions, unchanged evidence and unresolved inventory; displays “assessor declares”, separately from “bytes verified” and “engine checks”.

Recommend coordinated protocol **3**, capability `source_assessment.v1`, closed schema regeneration and matching native/client/MCP updates. Today's protocol 2 clients reject added result members/variants. Capability advertisement alone is not schema negotiation. Existing wire version mismatch fails explicitly; do not down-convert an assessment-aware validation/approval into v2. If a v2 bridge is later desired, it requires an explicit contract decision; it is outside this recommendation. Preserve stored v2 validation/approval/receipt bytes as historical records; new view marks `unavailable_legacy`, not absent/clean. Do not migrate their hashes or authorize fresh commit from historical v2 evidence: require fresh v3 validation and applicable approval. Domain canonical schema v1/source/work payloads and C calculation remain unchanged. Workflow envelope version changes, not retroactive domain export reinterpretation. Assessment history export, if added, is a separately typed non-authoritative review bundle; canon export alone must never imply it contains assessments. Imported bundles require new local identity/authentication and fresh authority, never importing approvals/grants.
